Mission Control

Public hostname migration — ms-* → mc

Rename both public hostnames to match the project's own name — ms-prod.salsquared.xyz → mc.salsquared.xyz and ms-dev.salsquared.xyz → mc-dev.salsquared.xyz — by standing the new pair up fully gated alongside the old, cutting over, and retiring ms-* in the same session.

Context & problem

Problem

The project is Mission Control and abbreviates to mc everywhere it names itself internally: the LAN vhost is mc.local (~/.config/caddy/Caddyfile), the Pub/Sub signer service account is pubsub-mc-publisher@…, the outbound fetcher User-Agent strings say mc.local. The public surface is the one inconsistent thing: both tunnel hostnames were named ms-*.

This is cosmetic in the sense that nothing is broken, and load-bearing in the sense that the wrong name is copied forward every time someone reads the config. It has already leaked into two design docs' task lists and one prepared-but-unexecuted incident-recovery command (docs/next_steps.md:21). The cost of not doing it is that the mismatch keeps propagating; the cost of doing it is one carefully-ordered session across four external control planes.

The rename is exactly two hostnames:

Goals & non-goals

  • Goal: both public hostnames serve on mc.salsquared.xyz / mc-dev.salsquared.xyz, gated by Access exactly as before, with Gmail push ingest verified live on both tiers.
  • Goal: ms-* fully retired in the same session — no lingering hostnames, no orphan Access apps, no stale OAuth redirect URIs.
  • Goal: every live/canonical doc and functional repo reference reads mc, and the one executable stale command in docs/next_steps.md is corrected rather than left to mislead.
  • Non-goal — a repo-wide ms-* sweep. Dated review snapshots and docs/archive/* keep their historical text (OQ4). Rewriting a dated record makes it say something that was not true on its date.
  • Non-goal — touching the LAN surface. mc.local, the Caddyfile, and the loopback bind are out of scope. docs/multi-user-crew.html separately plans to retire the mc.local vhost and repoint launch-ms.sh:33-37's APP_URL; that is that doc's work. This doc only keeps the two consistent by renaming the script and its hostnames.
  • Non-goal — origin-side Access JWT verification. Unchanged from cloudflare-access-auth.html OQ3; the trust-edge posture is inherited as-is.
  • Non-goal — a redirect from ms-* to mc. Single-owner surface; the owner updates their own bookmarks. A permanent redirect would mean keeping the old hostnames, their Access apps, and their tunnel routes alive indefinitely — the opposite of the point.

Design

Approach — overlap, cut over, retire

There is no code to design here; the design is the ordering. The shape is a bounded overlap (OQ3): bring mc and mc-dev up fully gated alongside the live ms-* pair, verify them against the real edge, flip the origin's env and the two Pub/Sub subscriptions, confirm a Gmail round-trip on both tiers, then tear ms-* down — all in one session.

During the overlap window both hostname pairs route to the same origins. Nothing about the origin is per-hostname except PUBSUB_AUDIENCE (asserted against the OIDC aud claim) and NEXTAUTH_URL (the OAuth callback base) — so serving four hostnames off two ports is not a special mode, it is just two extra tunnel routes.

The security invariant — Access before routing, routing before teardown

A hostname that routes through the tunnel before its Access app exists is wide open to the public internet. The origin does not verify the Access JWT (trust-edge, cloudflare-access-auth.html OQ3a) — it treats every arriving request as the owner. So the edge gate is the only gate, and a routed-but-ungated hostname hands an anonymous visitor a fully-authenticated session on the owner's job-search data, resume store, and Gmail-derived application records.

That yields a strict ordering, and its exact mirror on teardown:

  • Build-up (P1): Access apps → DNS → tunnel routes. The Access app is created for a hostname that doesn't resolve yet, which is harmless. DNS resolving to the tunnel is harmless while the tunnel has no route for that hostname (it returns a Cloudflare error, never the origin). Only the tunnel route makes traffic flow — and by then the gate is already in front of it.
  • Teardown (P4): tunnel routes → DNS → Access apps. Removing the route stops traffic reaching the origin first; DNS goes next; the Access app is deleted last. Deleting an Access app while its hostname still routes leaves that hostname ungated for the length of the gap — the exact failure the build-up order exists to prevent.

This mirrors the original rollout's "edge live before code" prerequisite (cloudflare-access-auth.html, P4 → P1 dependency). Same invariant, applied to a hostname instead of a code deploy.

The webhook audience window

app/api/gmail/webhook/route.ts:19-25 reads PUBSUB_AUDIENCE and hands it to verifyPubSubOIDC(req, audience), which requires the token's aud claim to equal it exactly. Pub/Sub mints that claim from the subscription's --push-auth-token-audience. Those two values live in different control planes, so they cannot be changed atomically — there is necessarily a window where they disagree and every push is rejected.

The failure mode is symmetric — either order produces the same outcome (an aud mismatch → the route returns 401 before any ingest work), and either way it is self-healing: Pub/Sub retries undelivered messages on backoff (≤600s) across a 7-day retention window, and the webhook is idempotent on redelivery (INSERT OR IGNORE on WebhookDelivery(messageId), then resume from min(user.lastSyncedHistoryId, envelope.historyId)). Nothing is lost; deliveries just queue.

The window duration is not symmetric, and that decides the order. Flip the origin first (env edit → build → pm2 restart --update-env), then the subscription:

  • The env edit is inert until the restart — the running process holds the old value — so the slow half (a prod npm run build) happens entirely while the old audience is still in force and pushes still succeed.
  • The window opens the moment the restart completes and closes when modify-push-config returns: two fast gcloud calls, seconds.
  • The reverse order would open the window before the build and hold it open across build + restart — minutes of rejected pushes for no benefit.

The two tiers are independent (separate env files, separate subscriptions, separate ports), so each tier's window is its own and can be closed before the other is opened.

Executing the edge change — scripted, not clicked

The edge work is 8 discrete mutations (4 Access apps, 2 DNS records, 2 tunnel routes) plus 8 more on teardown. Per OQ2 these run through a scoped Cloudflare API token the owner creates, not through the dashboard. Required scopes:

ScopeResourceUsed for
Zone → DNS → Editzone salsquared.xyzcreate/delete the mc + mc-dev CNAMEs
Account → Cloudflare Tunnel → Editaccountread + write the tunnel's public-hostname configuration
Account → Access: Apps and Policies → Editaccountcreate/delete the 4 Access apps + their policies

That token can create publicly-reachable routes and delete access policies — it is the most privileged credential in this migration. It is created for this session and deleted at the end (P4.5).

One API shape matters: the tunnel configuration endpoint (PUT /accounts/{account_id}/cfd_tunnel/{tunnel_id}/configurations) takes the whole ingress document, not a patch. Every write is therefore a read-modify-write of the JSON captured in P0.2, and the catch-all rule must stay last. This is also why P0.3 snapshots that JSON verbatim: it is both the rollback artifact and the source of the origin service values.

Doc strategy — amend the decision record, don't find/replace

Most doc updates are mechanical hostname swaps. One is not. docs/cloudflare-access-auth.html contains OPEN-A (lines ~238-240 in the risk table and ~298-305 in Open Questions), which on 2026-06-24 explicitly weighed ms.salsquared.xyz against ms-prod.salsquared.xyz and decided (a) ms-prod on the grounds that it "matches everything already deployed" and needs "no env or Pub/Sub change."

Alternatives considered

  • Hard cutover — rename in place, no overlap. Delete the ms-* routes and create the mc ones in the same breath. Rejected (OQ3): there is a window where neither hostname works, and if the origin service value read in P0.2 turns out wrong there is nothing left to fall back to. The overlap costs two extra tunnel routes for one session and buys a verified-before-you-commit path.
  • Open-ended grace period — keep ms-* for weeks. Rejected (OQ3): it means maintaining 8 Access apps and 4 live public hostnames indefinitely, doubling the surface that must stay correctly gated, with no benefit for a single-owner deployment where the only client is the owner's own browser and one Pub/Sub subscription.
  • Redirect ms-* → mc permanently. Rejected: a redirect is not a retirement — it keeps both hostnames, both Access apps, and both tunnel routes alive forever, which is the state this change exists to eliminate. One owner, one bookmark update.
  • mc-prod for symmetry with mc-dev. Rejected: prod is the surface actually used daily and the one typed on a phone; the unqualified name should be the default tier. The asymmetry is deliberate and self-documenting — mc is the thing, mc-dev is the variant.
  • Manual dashboard execution of the edge changes. Rejected (OQ2): 16 mutations across three Cloudflare product surfaces, several of which are security-relevant (a mistyped hostname on an Access app leaves the real one ungated). Scripted calls are reviewable, re-runnable, and diffable against the P0.3 snapshot.
  • Repo-wide ms-* sweep including archives. Rejected (OQ4): archive docs and dated review snapshots are historical records. Rewriting docs/archive/gmail-realtime-push.html to say mc would make it claim the 2026-05-29 Pub/Sub wiring used a hostname that did not exist for another 14 months.
  • Leave launch-ms.sh alone. Rejected (OQ1): it is the same ms-for-mc error, its inbound references are all in docs already being edited, and a git mv is cheap now and annoying later once docs/multi-user-crew.html's P4.1 starts editing the script's contents.

Risks & mitigations

Rollback

The overlap exists precisely so that every phase is reversible while ms-* is still live. Per phase:

PhaseRevertCost
P0 prerequisitesNothing was changed — the token can simply be deleted.none
P1 additive edgeDelete the 2 tunnel routes, then the 2 DNS records, then the 4 Access apps (teardown order — do not delete an Access app while its route lives). ms-* was never touched and keeps serving throughout.none — no user-visible impact at any point
P2 OAuth URIsRemove the two added redirect URIs. Purely additive; the ms-* URIs are still present.none
P3 cutoverRestore the two tier env files to ms-*, revert next.config.ts:25, rebuild, pm2 restart … --update-env, then re-run the two modify-push-config calls with the ms-* endpoint + audience. Same origin-first ordering; same seconds-long aud window; same self-healing retry.one rebuild + restart cycle; queued pushes drain
P4 teardownRe-create what was removed: tunnel routes and DNS records from the P0.3 snapshot, Access apps from the recorded policies (Allow email salsalcedo4321@gmail.com; prod 24h, dev 1 month; two path-scoped Bypass apps). Re-create in build-up order: Access apps → DNS → routes.manual re-creation + DNS propagation delay
P5 repogit revert the commit. Pure text + a file rename; no schema, no data, no build artifacts.trivial

Point of no return. Nothing here destroys data, so there is no hard one-way door — but there is a practical one: P4.1, removing the ms-* tunnel routes. Before it, rollback is a config flip with both hostnames serving. After it, ms-* stops reaching the origin and anything still pointed at it — a bookmark, the un-reinstalled PWA, a copy-pasted gcloud command — fails until the route is re-added; P4.2's DNS deletion adds propagation delay on top. So P3.5 (verified Gmail round-trip on both tiers over the new hostnames) is the gate on entering P4. Do not begin teardown on an unverified cutover.

OQ1 — Should launch-ms.sh be renamed as part of this migration?
  • (a) Rename to launch-mc.sh now. git mv launch-ms.sh launch-mc.sh and update its 5 live inbound references (CLAUDE.md:30, docs/architecture.html:46,109,521,526,572, README.md:38,41, docs/multi-user-crew.html, docs/next_steps.md:16,342), leaving the script's own mc.local Caddy lines untouched. Cons: a rename in a migration commit slightly widens the diff, and any muscle-memory invocation of ./launch-ms.sh breaks.
  • (b) Leave the script alone; hostnames only. Change only the two public hostnames and their references. Effect: the repo keeps a launch-ms.sh whose name contradicts every other mc reference. Pros: tightest possible diff, strictly one concern per change. OQ2 — Who performs the Cloudflare edge changes, and how?
  • (a) Owner clicks through the Zero Trust + DNS dashboards. All 16 mutations (4 Access apps up, 2 DNS, 2 tunnel routes, then the same 8 down) are performed by hand in the UI. Effect: no credential is created, and nothing about the migration is automatable or re-runnable. Pros: no privileged token exists to leak or forget about; the UI validates some inputs. Cons: click-error risk across 4 Access apps, 2 tunnel routes, and 2 DNS records — and a mistyped hostname on an Access app is a silent security failure (the real hostname stays ungated while the dashboard looks correct); nothing is diffable against the P0.3 snapshot; teardown repeats the whole exercise.
  • (b) Owner creates a scoped API token; the change is scripted. A token limited to Zone → DNS → Edit (zone salsquared.xyz), Account → Cloudflare Tunnel → Edit, and Account → Access: Apps and Policies → Edit drives the mutations as reviewable API calls, with the tunnel configuration read first and written back as a read-modify-write. Effect: every edge change is an inspectable request, verifiable against the snapshot, and the teardown is the same script in reverse. Pros: eliminates click error on the security-relevant steps; the tunnel config becomes readable at all (P0.2 is impossible from the dashboard alone in scripted form); repeatable rollback. Cons: creates a genuinely privileged credential that must be scoped tightly and deleted afterwards.

✓ Decided: (b) — the owner creates a scoped Cloudflare API token and the edge work is scripted, because the ordering invariant (Access before routing) is only as good as the hostnames actually typed, and 16 hand-entered mutations across three product surfaces is exactly the shape of change where a single typo is both easy and invisible. The token's privilege is real, so it is scoped to three permissions and its deletion is an explicit task (P4.5), not a note.

OQ3 — How long do the old and new hostnames coexist?
  • (a) Hard cutover — no overlap. Rename the tunnel routes and DNS records in place, swapping ms-* for mc in one operation, with the Access apps re-pointed at the same time. Cons: there is a window where nothing works, and if the P0.2 origin-service value turns out wrong there is no live fallback to diagnose against — the only path forward is forward.
  • (b) Bounded overlap, retired the same session. Cons: 8 Access apps and 4 routes exist transiently, and the session must be seen through to the teardown rather than left half-done.
  • (c) Open-ended grace period. Bring mc up and keep ms-* alive for weeks before deciding to retire it. Effect: the doubled surface becomes the steady state. Pros: no deadline pressure; stale bookmarks keep working indefinitely. Cons: permanently maintains 8 Access apps and 4 public hostnames — twice the surface that must stay correctly gated — for a single-owner deployment whose only clients are the owner's browser and one Pub/Sub subscription; migrations left half-finished tend to stay half-finished.

✓ Decided: (b) — bounded overlap, retired in the same session, because the one genuinely unknown input (the tunnel's origin service target) is best validated against a still-working control, and the doubled-surface cost that makes (c) unattractive is precisely what makes (b) safe when it lasts hours instead of weeks. Rounds. A round is a dependency-barrier batch dispatched at once. Two tracks run concurrently throughout: the edge track (P0→P4, mostly serial by construction) and the repo track (P5.1–P5.9, almost fully parallel).

  • Round 1 (start immediately): P0.1 (owner, manual) ∥ the entire repo batch P5.1, P5.2, P5.3, P5.4, P5.5, P5.6, P5.7, P5.9 — 8 file-disjoint agents. Peak parallelism of the plan.
  • Round 2: P0.2 → P0.3 (serial; the tunnel document is single-writer).
  • Round 3: P1.1 (its four apps fan out) — barrier — P1.2 (two records fan out) — barrier — P1.3 — P1.4. The barriers here are the security invariant, not scheduling conservatism; they do not compress.
  • Round 4: P2.1 ∥ P3.1 ∥ P3.2 ∥ P4.6.
  • Round 5: P3.3 → P3.4 → P3.5. Serial, and the P3.3 → P3.4 handoff should be immediate — that gap is the audience window.
  • Round 6: P4.1 — barrier — P4.2 ∥ P4.3 ∥ P4.4 → P4.5.
  • Round 7: P5.8 (session entry needs the outcome) → P5.10 commit + push.

Critical path: P0.1 → P0.2 → P0.3 → P1.1 → P1.2 → P1.3 → P1.4 → P3.1 → P3.3 → P3.4 → P3.5 → P4.1 → P4.3 → P4.5 — 14 nodes, essentially the whole edge track. The repo track (P5.1–P5.9) is entirely off the critical path and adds nothing to wall-clock; only P5.10 waits, and it waits on P3, not on P5.

Most-constrained node: P0.2. It is owner-gated (needs the token from P0.1), single-writer, unreadable from this machine, and everything downstream on the edge track depends on the value it returns. Schedule it first and do not let the repo batch's progress create the illusion that the migration is moving — nothing on the edge can start until P0.2 has been read.

Wall-clock floor is set by two things the DAG can't compress: DNS propagation between P1.2 and P1.3, and the prod npm run build inside P3.3. Everything else on the path is an API call or a curl assertion.
