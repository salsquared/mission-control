Owner / Crew — two-role multi-user

Turn the single-owner app into a two-role app: the owner keeps everything, crew (friends & family) get only the job-search and resume surfaces — one project, one deployment, role-gated at the guard layer.

Context & problem
This doc supersedes two standing decisions, and closes one open requirement.
  • docs/cloudflare-access-auth.html:63 — "Non-goal: Multi-user / team support. The design is deliberately single-owner; revisit only if a second user is ever added." A second user is now being added, so that line is superseded by this doc, not silently contradicted.
  • That doc's OQ3b declined origin-side verification of Cf-Access-Jwt-Assertion as "redundant in the current single-owner topology" (cloudflare-access-auth.html:283). That reasoning expires at the second user and this doc reverses it — see §2.7 and OQ13. When there is one legitimate identity, a forged identity header buys an attacker nothing they did not already have; when there are several, it buys them somebody else's account.
  • docs/user-stories.md S15.20 — "the same gate applies whether I reach the app via localhost, mc.local, the phone-on-WiFi LAN IP, or the public Cloudflare-tunnel hostname. No network-based bypass." That requirement was written by the user, and the Access change left it unclosed (it moved the gate to the edge but kept the origin's implicit LAN trust). OQ2 and OQ13 close it. Note the nuance: S15.x's passcode mechanism is superseded (user-stories.md:145) but its stated requirement was not — it is satisfied here by a different mechanism.

The "trust the edge" argument survives only in a narrowed form: the edge is still the gate, but it no longer merely proves that the requester is authorized — it proves which person they are, the origin must read that identity rather than assume one, and the origin must now verify that the identity came from the edge at all.

Problem

Mission Control is a job-search / resume / research / space / finance dashboard that runs on the owner's Mac behind a Cloudflare tunnel, gated at the Cloudflare Access edge. Friends and family want the job-search half of it: application tracking, job-posting watchlists, the profile/bullet library, and resume generation. Today they cannot have it — not because the data model resists (it does not; see §2.11), but because the origin has exactly one notion of identity:

  • lib/owner.ts:resolveOwner() resolves "the owner" and memoizes it at module level (lib/owner.ts:50). All three guards in lib/auth-guards.ts call it and synthesize an owner session — every request that reaches the origin is served as the owner.
  • OWNER_EMAIL is unset in .env (audited 2026-07-26), so resolveOwner() currently falls to branch (2) — user.findFirst({ orderBy: { id: 'asc' } }), lib/owner.ts:89. With one User row per DB that is exactly right. The moment a second row exists it becomes "whoever has the lowest cuid".
  • There is a second owner resolver, lib/user-scope.ts:resolveOwnerUserId() (allowlist-first, then sole-user, then the legacy id='global' settings row), also module-memoized. Both must be reconciled.
  • The SSE stream has no notion of ownership at all: ServerEvent (lib/events.ts:3) carries no userId, and broadcastEvent() fans out to one process-global listener Set.
  • Every Gemini call goes through one cross-tier shared token bucket at 12 req/min on the owner's API key (lib/ai/rate-limit.ts:42, data/gemini-bucket.db), with no per-user fairness.

Doing nothing costs nothing technically — but the job-search surfaces are the most complete and most useful part of the app, and the alternative asks (a fork, a second deployment) are strictly worse for a one-person maintainer (see §2.15).

What is already multi-user-ready

Most of the hard work is done. These are not re-solved by this design — they are load-bearing prerequisites that already hold:

  • The schema is userId-scoped throughout, with per-user compound unique keys: Application @@unique([userId, normalizedCompany, normalizedRole, track]), SavedPaper @@unique([userId, paperId]), Canon @@unique([userId, slug]), BlacklistedCompany @@unique([userId, normalizedName]). GlobalSetting is one row per user (userId @unique, prisma/schema.prisma:71-101). Every User relation is onDelete: Cascade — verified by grep, zero exceptions — which is what makes crew removal a one-liner (§3.3).
  • The formerly-global tables were already scoped in the P2.2 pass (migration 20260612235207_scope_user_tables_per_userid): Task, LifeGoal, GlobalSetting, SavedPaper.
  • The Gmail webhook already resolves its user from the Pub/Sub envelope, not the owner (app/api/gmail/webhook/route.ts:79).
  • The scheduler is per-user at the row level. All 12 jobs iterate rows carrying userId; gmail-watch-renew.ts:61-68 loops every Google-linked user. (One exception found — see §2.6.)
  • 65 of 67 routes are guarded. The two exceptions are deliberate: auth/[...nextauth] (NextAuth handler, gated by ALLOWED_SIGNIN_EMAILS in the signIn callback) and gmail/webhook (OIDC-verified via verifyPubSubOIDC).
  • No cross-user cache leak today. The 10 withCache routes without userKeyFn all return global data; the 4 withSharedCache routes are global arXiv/HF data. No user-scoped route is cached at all.
  • Cloudflare Access already provides per-person identity for free. .env carries CLOUDFLARE_GOOGLE_OAUTH_CLIENT_ID/_SECRET, so Access authenticates against Google as IdP and forwards Cf-Access-Authenticated-User-Email to the origin. Adding crew is an edge-policy edit, not code.

Goals & non-goals

  • Goal: A second role, crew, can sign in through Cloudflare Access with their own Google account and use only the job + resume surfaces, with their own applications, watchlists, postings, profile, canons and resumes — fully isolated from the owner's and from each other's.
  • Goal: Role enforcement lives server-side at the guard layer, statically verifiable, and covered by the existing pre-push hermetic gate. Every one of the 67 routes has an explicit, tested classification.
  • Goal: The diff stays centralized. Viewer identity is resolved in one new module; the 104 guard call sites keep their signatures and their session.user.* reads.
  • Goal: One identity path, no network-based bypass. Every browser-facing request — the owner's included — is identified by the Cloudflare Access identity header and nothing else. A header-less request is not a trusted request; resolveViewer() has exactly one identity source and zero fallback branches (OQ2). This closes S15.20.
  • Goal: The origin proves the identity header came from the edge rather than from a LAN client that typed it, via loopback binding plus Cf-Access-Jwt-Assertion verification (OQ13). Both layers ship in this change, not as later hardening.
  • Goal: The machine paths are untouched: the Pulsar service-token branch of requireSessionOrService and the OIDC-verified Gmail push webhook keep working byte-for-byte.
  • Goal: The owner's in-app experience is unchanged — same dashes, same data, no in-app sign-in wall. What does change, deliberately, is the route in: the owner reaches prod through mc.salsquared.xyz like everyone else, and mc.local / localhost:3101 stop being a way in (§2.7).
  • Non-goal: An admin UI for provisioning, promoting, or removing crew. v1 provisioning is manual — the owner adds an Access-policy email and inserts a User row via tsx. Deferred until there is a second reason to build a settings surface.
  • Non-goal: A permission model richer than the binary role. No per-dash grants, no clearance axis, no groups. Deferred until a second privilege axis actually exists.
  • Non-goal: Sharing anything between users — no shared watchlists, no shared postings feed, no visibility of one person's pipeline by another. Isolation is the whole product.
  • Non-goal: Preserving LAN reachability of the prod tier. mc.local's prod vhost is retired and prod binds to loopback — deliberately, because a LAN client can forge the identity header (OQ13). On-box recovery keeps a loopback-only, explicit-env break-glass; the dev tier keeps a separate dev-only one for the integration suites (OQ14).
  • Non-goal (v1): Per-minute Gemini fairness at the true chokepoint (acquireGeminiSlot). v1 caps at the route boundary instead — see §2.9 and OQ7.
  • Non-goal: New notification delivery wiring. Crew get the in-app bell (their own rows, already scoped); email delivery for crew degrades to the existing emailError path. One correctness fix to a hardcoded owner read is in scope (§2.6); no new features are wired into dispatchNotification.

Design

Approach at a glance

Seven changes, in dependency order. Everything else follows from them.

  1. Set OWNER_EMAIL. A configuration change that must land before anything else, because owner resolution is currently a lowest-cuid heuristic. This is a hard prerequisite, not a task ordering preference (§3.1, R3).
  2. User.role — one additive column, "owner" | "crew".
  3. lib/viewer.ts:resolveViewer() — the single new identity chokepoint. Reads Cf-Access-Authenticated-User-Email via await headers(), looks up the User row, returns { id, email, role }. No memoization, and no fallback identity.
  4. Close the network bypass and authenticate the header — bind prod to loopback, retire the mc.local prod vhost, and verify Cf-Access-Jwt-Assertion against the team JWKS. Without this, role gating is decorative: any LAN client could type somebody else's email into a header (§2.7).
  5. A fourth guard, requireOwner(), with the same return shape as requireSession(). Owner-only routes swap their guard import; nothing inside a handler changes.
  6. Per-user SSE fan-out — ServerEvent gains a user scope, and subscribers only receive their own events.
  7. Per-user config & budget isolation — the findGlobalSetting() reads that silently return the owner's config become viewer-scoped, and a per-user daily Gemini cap bounds the worst case.

Viewer resolution — the one new chokepoint

New module lib/viewer.ts, deliberately small:

export type Role = 'owner' | 'crew';
export interface Viewer { id: string; email: string; role: Role }

export async function resolveViewer(): Promise<Viewer | null>

Resolution order — one identity source, zero fallback branches (OQ2):

  1. Verify Cf-Access-Jwt-Assertion (§2.7, Layer 2). Fails or absent → return null.
  2. Read cf-access-authenticated-user-email from await headers(). Trim + lowercase. Absent → return null.
  3. prisma.user.findUnique({ where: { email }, select: { id, email, role } }). Hit → that viewer. Miss → return null plus one loud console.warn naming the email (OQ3).
  4. null → the guards 401. The response body points at https://mc.salsquared.xyz so the failure is self-explaining rather than a bare 401.
The try/catch must yield "no viewer", never "owner". headers() throws outside a request scope — route-auth-smoke.ts:8 documents exactly this ("Calling a route handler directly from a standalone tsx script throws 'headers() called outside a request scope'"), and five hermetic smokes plus the scheduler are in that position. Because there is no owner fallback any more, the catch block must resolve to null. Wiring it to resolveOwner() "so tests keep working" would silently reinstate the bypass this design exists to remove — and it would do so on a path with no request, i.e. reachable from anything that imports a guard. The break-glass paths below are separate, explicit branches gated on an env var; they are never the catch block.

Why headers() and not a threaded req: requireSession() takes no request argument and has 72 call sites (104 across all three guards). next/headers is currently imported nowhere in the codebase, so this is a new dependency — but it is the standard Route-Handler mechanism, it is available in Next 16.2.9 (async headers()), and it keeps this change the same shape as the original Cloudflare Access change: rewrite the guards, touch no handler. (OQ1a.)

Break-glass — two narrow, explicit, loudly-logged escapes

Removing the LAN fallback removes two things that were load-bearing for non-browser use. Each gets a purpose-built escape rather than a general trust rule:

  • Dev tier, for the 10 integration suites (OQ14). scripts/tests/integration/*.ts all call http://localhost:4101 with no identity header — verified: 10 files, all 10 reference 4101. An env var (e.g. MC_DEV_LOOPBACK_OWNER=1), off by default, makes a loopback request on the dev tier resolve to the owner, with one console.warn per process so it is visible in the in-app log viewer. Guarded three ways: the env var, NODE_ENV !== 'production', and a loopback remote-address check. Dev is owner-only (OQ12), so this grants nothing that is not already the only identity on that tier. It can never be enabled on prod — the production guard is a hard code condition, not a convention.
  • On-box recovery for prod. Same shape, separate var, same three guards minus the dev-tier condition — for the case where the tunnel or Access is down and the owner needs the app from the console. Off by default; setting it is a deliberate act with a log line attached.
  • Interaction with §2.7 Layer 2: JWT verification must be skipped on a break-glass path, because a loopback request has no Cf-Access-Jwt-Assertion to verify. The branch order is therefore: break-glass check first (and if it fires, skip step 1), otherwise the strict path. Getting this backwards makes the break-glass dead code and the integration suites fail with a confusing JWT error.
The memoization trap — read this before writing lib/viewer.ts. lib/owner.ts memoizes at module level (let cachedOwner: Owner | null, lib/owner.ts:50). That is correct for the owner — the owner genuinely never changes for a process lifetime. Copying the pattern into resolveViewer() is a total authorization bypass: the first request after a restart would populate the memo, and every subsequent viewer would be served that identity — a crew member's request would return the owner's rows, and vice versa. A module-level memo is not an optimization here, it is a defect. v1 uses no viewer memo at all — one findUnique on an indexed unique column per request, against a local SQLite file, is sub-millisecond and is not worth risking. If a memo is ever added it must be a bounded Map keyed by email with a short TTL, and the smoke below must still pass.

Guarding the trap: a hermetic smoke (scripts/tests/hermetic/viewer-resolution-smoke.ts) that resolves two different header emails back-to-back and asserts two different viewers, plus the no-header fallback and the unknown-email case. It goes into the pre-push gate, which auto-discovers new files under scripts/tests/hermetic/.

Role gating — one new guard plus a manifest test

Decision: enforce at the guard layer. Add a fourth guard to lib/auth-guards.ts with the same return shape as requireSession():

export async function requireOwner()                              // 403 for crew
export async function requireOwnerOrService(req, cfg)             // owner branch + unchanged Bearer branch

An owner-only route changes by exactly two tokens — the import and the call. Handler bodies, session.user.id reads, and error wiring are untouched. The synthesized session gains role ({ session: { user: { id, email, role } } }) — purely additive, so existing reads keep working and the handful of places that want the role (the postings feed, the quota check) get it without a second lookup.

Why the guard layer wins — it is the only option that plugs into machinery the repo already has:

  • scripts/gen-api-docs.ts detects any identifier imported from lib/auth-guards and invoked, and renders it as an auth chip (gen-api-docs.ts:190-195, :310). requireOwner therefore appears in docs/apis.html for free — a human-auditable, generated role map, with no new tooling.
  • scripts/tests/hermetic/route-auth-smoke.ts already asserts per-route guard identity structurally (import present, awaited, error-wired) for 19 routes. Extending its ROUTES array to all 67 with a role: 'owner' | 'any' field gives the property a route manifest would have given — a new route with no classification fails the push — without introducing a runtime layer.

Two invariants to state loudly:

Hiding a dash is not access control. The role-filtered dash set (§2.10) is UX only. Every owner-only surface is enforced server-side by requireOwner(); the client filter merely stops crew being shown doors that would 403. Any future "just hide the card" change to an owner-only capability is a bug.
Every crew-allowed route must scope its queries by the viewer's id. All 39 already do — spot-verified: app/api/postings/route.ts:101-107 scopes through a { watchlist: { userId } } join, app/api/resumes/[id]/download/route.ts:32 uses where: { id, userId }, app/api/applications/events/route.ts:158-163 re-checks existing.application.userId !== userId. The corollary invariant, inherited from lib/cache.ts:279-281: any newly-cached user-scoped route MUST pass userKeyFn.

Header authenticity — closing the forgery path

Role gating is decorative without this section. Cf-Access-Authenticated-User-Email is just a header. Any client that can open a TCP connection to the origin can set it to any value. Rejecting header-less requests (OQ2) does nothing against a forged one — so with crew accounts in existence, a LAN client could send Cf-Access-Authenticated-User-Email: <owner> and be served as the owner, or send a crew member's address and read their pipeline. Two layers close it, and both ship in this change (OQ13a).

Layer 1 — remove the unauthenticated route to the origin (config, no code)

Three facts make this concrete, all verified on the box:

  • next start -p 3101 has no -H (package.json:8), so prod binds all interfaces; PM2 launches it as npm run start -- -p 3101 (ecosystem.config.cjs:7). Add -H 127.0.0.1.
  • Loopback binding alone does NOT close the LAN path. Caddy runs --config /opt/homebrew/etc/Caddyfile (confirmed from the live process args) and that config is mc.local:443 { tls internal; reverse_proxy 127.0.0.1:3101 } — a LAN-reachable listener proxying to loopback. So retiring the mc.local prod vhost is load-bearing, not cosmetic.
  • There is only ONE Caddyfile. /opt/homebrew/etc/Caddyfile is a symlink to ~/.config/caddy/Caddyfile (lrwxr-xr-x … -> /Users/sal/.config/caddy/Caddyfile), exactly as launch-mc.sh:27's one-time setup documents (ln -sf). Edit the real file at ~/.config/caddy/Caddyfile; editing "both" is not needed and there is no stale duplicate to chase. Verify with ls -la /opt/homebrew/etc/Caddyfile before touching either path.

Consequential follow-ons: launch-mc.sh:33-37 picks APP_URL="https://mc.local" when Caddy is running and falls back to http://localhost:$PORT — both die under this change and must be repointed at https://mc.salsquared.xyz. Its line 31 comment ("Add to .env: NEXTAUTH_URL=https://mc.local") is stale already — the real env is NEXTAUTH_URL="https://mc.salsquared.xyz" (and mc-dev for dev), so the Google connect redirect is not affected by retiring the vhost. Delete the comment. The ~11 mc.local occurrences in fetcher User-Agent strings (+https://mc.local; personal job-search agent) are outbound politeness labels — leave them alone.

Layer 2 — verify the Access JWT (code)

Layer 1 is a configuration property, and configuration regresses: a future next start tweak, a restored Caddyfile, or a new reverse proxy silently reopens it. Layer 2 makes forgery fail cryptographically regardless. New module lib/access-jwt.ts:

This is no longer hypothetical — it happened on 2026-07-28, before any crew account existed. During the hostname migration, DNS and the tunnel were repointed to mc while the four Access apps were still bound to the old ms-* hostnames, so both public hostnames served with no Access app in front of them for roughly 14 minutes (03:30:09Z → ~03:44Z; commit f368415, and hostname-ms-to-mc.html §3 records the ordering invariant derived from it). Because the origin trusts the edge and performs no independent check, the app served owner-authenticated data to anonymous requests on the public internet for the whole window — no forged header required, no LAN access required. Layer 2 is exactly what converts that class of edge-side misconfiguration from a total data exposure into a stack of 401s: with JWT verification in place the same 14 minutes would have been an outage, not a breach. Note the asymmetry this creates once crew exist — an ungated window would expose everyone's pipeline, not just the owner's, which is why OQ13 ships both layers in this change rather than deferring Layer 2 as hardening.
  • Fetch the team JWKS from https://<team>.cloudflareaccess.com/cdn-cgi/access/certs, cache it in module memory with a TTL and a refresh-on-unknown-kid path (key rotation must not require a restart).
  • Verify Cf-Access-Jwt-Assertion: RS256 signature, iss = the team domain, aud = the per-app AUD, plus exp/nbf. Any failure → null, i.e. no viewer.
  • Cross-check: the verified token's email claim must equal the Cf-Access-Authenticated-User-Email header. A mismatch means one of them was tampered with — reject. (Once this holds, the header is strictly redundant; it is kept because it is the documented, stable surface and the JWT claim shape is Cloudflare's to change.)
  • New env: the team domain and a per-app AUD per hostname (prod and dev differ). Both go in .env.{development,production}.example. Live values as of the 2026-07-27 hostname migration — team salsquared.cloudflareaccess.com, so the JWKS is https://salsquared.cloudflareaccess.com/cdn-cgi/access/certs; AUD 2ed7bc0e82620032d1b9b2cd3ef1f028c554cf3635e147a73f16f158cfb4b10f for mc.salsquared.xyz and 3f95011a1cdada25918c7b92aca8bec36590d0ca0c10da3e95da1e5146a37c96 for mc-dev.salsquared.xyz. Both were read from the unauthenticated Access login redirect (the kid query parameter, cross-confirmed against the aud claim of the meta token in the same response) — an AUD is an application identifier, not a secret.
  • An AUD rotates whenever its Access app is recreated — but not when it is edited. The ms-* → mc migration ended up repointing the four existing apps in place, preserving their policies (commit f368415) rather than executing hostname-ms-to-mc.html's planned create-new/delete-old (its P1.1 + P4.3), so these AUDs survived the rename and the values above are the same apps under new hostnames. The invariant still binds for any future change that replaces an app: because Layer 2 is fail-closed by contract, a stale AUD in env is not a degraded mode — it is a total lockout of every user on that hostname, the owner included, with the break-glass path (§2.3) as the only way back in. Treat "re-read the AUD and restart the tier" as part of any app rebuild or Zero Trust reorganisation, not as follow-up work.
  • Fail-closed, deliberately. Unlike the caches and the rate buckets — which are best-effort by design — an unavailable JWKS must 401, not admit. A network blip that degrades to "trust the header" would be the bypass with extra steps. The JWKS cache TTL is what absorbs transient failures.
  • Skipped on the break-glass paths only (§2.3), since a loopback request has no JWT. Branch order: break-glass first, else strict.

Gemini budget and the LLM cache

Crew reach a lot of Gemini: resumes (resume-rewrite on MODEL_FLASH, resume-tagline, posting-parse), resumes/specialize, profile/bullets/assist, profile/tagline/draft, profile/import (import-llm + synthesize + auto-tag), discovery/suggest, watchlists/[id]/run (employment-type classify). All of it spends the owner's GOOGLE_GENERATIVE_AI_KEY against one shared 12/min cross-tier bucket.

Two things already protect against the unbounded case, and should not be rebuilt:

  • GEMINI_RATE_BURST (default 60, ~5 minutes of backlog) makes acquireGeminiSlot() fail-fast rather than accumulate an unbounded queue (lib/ai/rate-limit.ts:100-104). It bounds the backlog; it does not prevent starvation.

What is not protected is starvation of the owner's Gmail ingest classifier. lib/email-parser.ts:parseApplicationEmail is the load-bearing consumer: if a crew member loops "regenerate resume", the ingest classifier queues behind them and the owner's applications stop being ingested from email. That is the failure this design must prevent, and it is what makes a per-user cap load-bearing rather than nice-to-have.

Design (OQ7 lean): a per-user daily credit counter at the route boundary. One additive model, one helper, called at the top of the LLM-bearing crew routes:

Alternatives considered

Two were decided before this doc and are recorded here so the reasoning is not re-litigated:

  • Fork into a slim friends-and-family app. Rejected. It would have to invent its own auth story from scratch (the whole point of the Access edge is that there is none to write); it would mean three deployments on one Mac; two codebases for one maintainer; and it would multiply the cross-tier shared-SQLite coordination that data/{llm-cache,research-cache,arxiv-bucket,gemini-bucket}.db already carefully serialize across four processes. Option C — one project, role-gated — was chosen.
  • Give crew the whole dashboard unchanged. Rejected. The research, space, and finance dashes are irrelevant to a job hunt, internal-systems is an ops surface that exposes the server log tail (every user's Prisma query parameters in prod), and the incremental cost of a role filter is one array predicate.
  • Naming: admin/member, owner/guest, flight-director/crew. Rejected in favor of owner/crew: admin/member is generic and fights the theme; owner/guest reads as temporary and second-class; flight-director/crew is purer but forces renaming everything already called owner (~104 guard call sites, OWNER_EMAIL, resolveOwner). owner/crew keeps the existing vocabulary at zero rename cost and fits the Mission Control metaphor. If privileges ever need a second axis, clearance is the theme-consistent word — do not build it until that axis exists.

Alternatives decided in this doc:

  • Per-route inline role checks instead of a guard. Rejected: more code in every handler, nothing to statically verify, and trivially forgettable on a new route — which is precisely the failure mode with the worst blast radius (§3.1, R1).
  • A central route manifest enforced in middleware.ts. Rejected on a hard technical ground: there is no middleware today, and Next middleware runs on the Edge runtime — it cannot touch Prisma, so it could not read User.role at all without a second identity channel. Path matching would also duplicate the filesystem router and be invisible at the call site. The manifest's one genuine virtue — "a new route without a classification is caught" — is captured instead by making the manifest a hermetic test in the pre-push gate (§2.4).
  • Threading req through the guards to get the identity header. Rejected (OQ1b): 104 signature changes would bury this design's ~15 substantive edits in mechanical noise, on precisely the diff that most needs a legible security review.
  • Keeping the LAN as a trusted network (the original OQ2 framing: no header ⇒ owner). Rejected: the premise was invalidated — the owner will have friends on the home WiFi using their own accounts, so "no header means owner" is a one-step impersonation of the owner by anyone on the network, and it leaves S15.20 unclosed. Replaced by a hard 401 plus two narrow, explicit break-glass branches.
  • Deferring Cf-Access-Jwt-Assertion verification as future hardening, per cloudflare-access-auth.html's OQ3b. Rejected (OQ13a): that decision's stated justification was redundancy "in the current single-owner topology", which is exactly the premise this change removes. Deferring it would leave role gating enforceable only by a configuration property (the loopback bind), and configuration regresses silently.
  • A per-user token bucket inside acquireGeminiSlot(). Deferred (OQ7b). It is the correct fix at the true chokepoint, but it requires threading a userId through ~15 lib modules and every scheduler caller. The route-boundary daily cap bounds the actual threat (a runaway loop) at a fraction of the diff; promote (b) if fairness, not bounding, becomes the complaint.
  • Collapsing requireLocalOrSession into requireSession. Deferred. Its LAN-bypass semantics are already dead, but the collapse touches 29 files for zero behavior change and would bloat the review surface of a security-sensitive diff.

Custodianship & blast radius

This is the risk that is not primarily technical, and it should be decided consciously rather than absorbed.

  • One file holds several people's identity. prisma/prod.db would contain each crew member's full Profile — resumes carry home address, phone number, and complete employment history — alongside every application they have ever tracked. It also contains the owner's plaintext Account.refresh_token, which is mailbox-equivalent credential material for the owner's Gmail.
  • The backup is now multi-person-sensitive. scripts/backup-db.sh snapshots that file and mirrors it to Google Drive via rclone. Age encryption is applied only when ~/.config/mission-control/backup.pub is present. Recommendation: make that key a hard prerequisite of this change — an unencrypted multi-person PII snapshot in cloud storage is a materially different exposure from an unencrypted single-owner one.
  • The host is a home Mac behind a residential connection, with no formal availability or incident story.
  • The owner can read everything, unavoidably. DB access is DB access; no role model changes that. This is not fixable, it is disclosable — tell crew in one plain sentence what is stored and who can see it, before they enter anything.
  • OQ6a materially shrinks this, and it is decided. Crew never connect Google, so no crew refresh_token ever lands in prod.db — the worst case stays "crew resumes and applications" rather than "crew mailboxes". This was the single largest custodianship lever available and it has been taken.

  3. Code — revert + rebuild. git revert the range → npm run build → pm2 restart mission-control --update-env and pm2 restart mission-control-scheduler-prod --update-env. Both new columns are additive and unread by the reverted code, so no migration-down is required; the reverted guards resolve the owner exactly as they do today. Before any of it: scripts/backup-db.sh for a pre-migration snapshot of both prod.db and data/resumes/. The full fresh-machine recovery path is in docs/backup-recovery.md.

OQ1 — How does resolveViewer() learn the request's identity?
  • (a) Read the header inside the resolver via await headers(). lib/viewer.ts imports headers from next/headers and reads cf-access-authenticated-user-email, wrapped in a try/catch because the dynamic API throws outside a request scope (hermetic smokes and the scheduler call the guards directly). Every guard signature — and therefore all 104 call sites — is untouched. Pros: the diff is confined to lib/viewer.ts + lib/auth-guards.ts, exactly the shape of the original Cloudflare Access change; requireSession() keeps taking no argument. Cons: introduces the codebase's first next/headers import; identity becomes implicit request-scoped state rather than an explicit parameter; the try/catch fallback path must be deliberately designed or the hermetic smokes silently exercise the wrong branch.
  • (b) Thread req through every guard. Change requireSession() → requireSession(req) and update all 72 call sites (plus 29 requireLocalOrSession, 3 requireSessionOrService), reading the header off req.headers. Pros: identity is an explicit parameter — no hidden async-local state, works identically in tests and any future non-Next context. Cons: a 104-file mechanical diff on the security-critical path, which buries the ~15 substantive changes in this design under noise and makes the review far harder; every future route must remember to pass req.

✓ Decided: (a) — read the header via await headers() inside resolveViewer(); the guards keep their signatures and all 104 call sites are untouched. The whole value of the previous Access change was that the guards' return shapes absorbed the change so no handler moved; giving that up for parameter explicitness costs 104 files of review noise on precisely the diff that most needs a legible review, and next/headers is the sanctioned Route-Handler mechanism in Next 16.2.9. One consequence hardened by OQ2: (a)'s try/catch around the out-of-request-scope throw must resolve to null, never to an identity — see §2.3's danger callout.

OQ2 — A request arrives with no Cf-Access-Authenticated-User-Email. What does the origin do?

Rewritten, not appended to. The original question asked "who is the viewer on a LAN request?" — which presupposed that a header-less request is a trusted request. That premise was invalidated: the owner will have friends on the home WiFi using their own accounts, so "no header ⇒ owner" is not a conservative default, it is a one-step impersonation path available to every device on the network. The question is therefore reframed from who to whether, and the old option (a) survives below only as the rejected (b).

  • (a) 401 — no fallback identity of any kind. resolveViewer() has exactly one identity source (the verified Access header) and zero fallback branches; a header-less request gets 401 with a response body pointing at https://mc.salsquared.xyz so the failure explains itself. The two non-browser cases that genuinely needed network trust get purpose-built, off-by-default, loudly-logged break-glass branches instead (loopback + explicit env; OQ14 covers the dev/test one). Pros: one identity path, no implicit trust anywhere; satisfies the user's own S15.20 ("No network-based bypass"), which the Access change left unclosed; the headers()-throws catch block has nothing to fall back to, so it cannot silently become a bypass. Cons: the owner loses mc.local / localhost:3101 as a route in and must use the tunnel hostname; two new env vars exist purely as escapes; launch-mc.sh and the 10 integration suites both need attention.
  • (b) Fall back to the owner — the original framing. No header → return resolveOwner()'s result with role: 'owner', preserving today's behaviour byte-for-byte. Pros: zero regression for LAN/kiosk use; hermetic smokes and integration suites keep working untouched; no new env surface. Cons: invalidated — with friends' devices on the same WiFi this hands owner-equivalent access to anyone who can reach mc.local:443 or :3101, and it makes the out-of-request-scope catch block a bypass reachable from anything that imports a guard.
  • (c) Pin the header-less viewer with a LAN_VIEWER_EMAIL env var. No header → look up that email; unset → 401. Pros: explicit rather than heuristic; nameable in config. Cons: duplicates OWNER_EMAIL in every realistic case and adds a drift surface between them; and it does not reduce the LAN's privilege at all — it only writes it down, so the impersonation path in (b) survives verbatim.

✓ Decided: (a) — no network-based bypass. A header-less request 401s; resolveViewer() has one identity source and zero fallback branches; on-box recovery and the integration suites get narrow, explicit, loudly-logged break-glass branches rather than a standing trust rule. (b) is not a conservative default once friends' devices share the network — it is the single cheapest way to become the owner — and (c) buys none of (a)'s safety while adding config. This closes docs/user-stories.md S15.20, a requirement the user wrote and the Access change left open. Note that (a) alone is not sufficient: rejecting header-less requests says nothing about forged ones, which is why OQ13 exists.

OQ3 — What happens when an Access-passed email has no matching User row?
  • (a) Reject with 403 and one loud console.warn. resolveViewer() returns null for an unknown email; the guards produce an error response and the log line names the email so the owner can provision deliberately (add the Access-policy email and insert the User row). Pros: the User table stays an intentional list; a mis-typed or over-broad Access policy cannot silently create accounts; the log line makes the intended-but-unprovisioned case obvious in the in-app log viewer. Cons: two-step provisioning, so a crew member's first visit fails until the owner runs a command — needs a legible error page rather than a bare 403.
  • (b) Auto-provision a role='crew' row. First Access-passed request for an unknown email creates the User. Pros: one-step onboarding — add the email to the Access policy and the person just works. Cons: the Access policy silently becomes the account-creation surface, so a policy widened by accident (an email domain, or an "Everyone" rule while debugging) provisions strangers; also races on concurrent first requests, needing an INSERT OR IGNORE-style guard.
  • (c) Auto-provision, but only for emails in a CREW_EMAILS env allowlist. Pros: one-step onboarding with an origin-side second gate. Cons: a third allowlist alongside the Access policy and ALLOWED_SIGNIN_EMAILS, and the owner still has to edit config on each addition — so it buys the convenience of (b) at nearly the ceremony of (a).

✓ Decided: (a) — reject unknown identities; provision by hand. With a handful of family members the two-step cost is a one-time command, and it keeps "who has an account" a decision the owner makes explicitly rather than a side effect of an edge-policy edit — exactly the mistake with the largest blast radius (R1, R11). Scope note discovered during verification: there is no production user.create path in the codebase — only the NextAuth adapter and test fixtures — so the provisioning script (scripts/manage-crew.ts: add / list / remove) is genuinely new work rather than a thin wrapper, and it is a first-class task (P5.4.1), not an afterthought.

OQ8 — What shape does the user scope take on ServerEvent?
  • (a) Discriminated union on the model. Split ModelName into user-scoped and global sets and define ServerEvent = UserServerEvent (userId required) | GlobalServerEvent (no userId). Pros: tsc enumerates every unmigrated call site and makes the wrong pairing impossible — a Cache event cannot carry a userId and an Application event cannot omit one; that co-variance is what actually prevents the mistake when ~55 call sites are being edited across ~20 files by parallel agents. Cons: the largest of the three diffs — every one of the ~55 lines must be touched — and consumers doing event.model === 'X' narrowing need a quick check (the client discards the event object entirely, so in practice only the type alias in hooks/useServerEvents.ts moves).
  • (b) Optional userId?, absent means fan out to everyone. Pros: smallest diff — only the ~14 user-scoped model call sites need editing, and the 2 global ones are already correct. Cons: fail-open in the worst way: a user-scoped broadcast that forgets userId compiles, passes tests, and silently fans out to every connected client — and since the savings versus (a) is only ~3 lines (there are just two global models), it buys almost nothing for a permanently unsafe default.
  • (c) Required userId: string | 'GLOBAL' on a single interface. Pros: tsc still forces every call site to state a scope, with no union to thread through consumers; simplest type change. Cons: nothing stops userId: 'GLOBAL' on an Application event, so a hurried implementer can re-create the leak while satisfying the compiler; and a magic string in the identity position invites exactly that.

✓ Decided: (a) — the discriminated union. Two verification results strengthen this. First, the real count is 68 call sites, not ~55 — a wider mechanical fan-out makes compiler-enforced correctness more valuable, not less, and it makes (b)'s fail-open default correspondingly more dangerous. Second, the only two truly global models are Cache and FinanceTick, so (b)'s smaller-diff argument is worth roughly three lines. OQ11 — What happens to the negative-filter gate in the cross-user classify-pending-employment-types sweep?

Re-scoped, not appended to. The original question asked whose filters should gate the sweep, and its options assumed the row's owner was cheaply reachable. That was wrong: the pending query selects only externalId, company, title, snippet, location — no userId, no watchlistId — and then dedupes by externalId so one classification serves every row sharing the hash. The estimate of "~5 extra lines" for a per-row scoping was therefore wrong, and more importantly the sweep's own comment states the premise multi-user breaks: "A global match means the posting is hidden on every watchlist, so excluding the whole externalId is safe." The real question is whether the gate belongs there at all.

  • (a) Remove the gate entirely. Delete the findGlobalSetting() read and the matchesNegativeFilters skip from the sweep (and their now-unused imports); the pending select stays exactly as it is. Every pending posting gets classified. Pros: correct for every user by construction — no user's postings are skipped because of another user's filters, and no ordering question arises; zero interaction with the cross-user dedup, which is the sweep's whole efficiency; smallest and most obviously-right diff. Cons: loses the Gemini-spend saving on legacy blacklisted rows, so the sweep pays once for a finite backlog of postings nobody wanted classified.
  • (b) Intersect all users' filters — skip an externalId only when every user's filter set matches it. Pros: keeps some spend saving while never wrongly skipping for any individual. Cons: requires reading every user's settings row per sweep and computing an intersection that, with even two people whose filters differ at all, degenerates to matching almost nothing — so it buys near-zero saving for real added complexity, on a path whose only job is to be cheap.
  • (c) Make the sweep per-user. Widen the pending select to carry watchlist.userId, group by user, and run the gate per group. Pros: per-user correct and keeps the full spend saving. Cons: abandons the cross-user externalId dedup that is the reason the sweep is cheap — the same posting on three people's watchlists would now be classified up to three times, so the "saving" is spent immediately on duplicate classification; and it is by far the largest change to the file.

✓ Decided: (a) — remove the gate. It is self-described defence-in-depth for legacy NULL-employmentType rows, and the job-watcher's ingestion drop (now correctly per-user, P2.3.2) already prevents new blacklisted postings from ever being stored — so the gate guards a shrinking, finite backlog. (b) collapses to no saving as soon as two people's filters differ, and (c) trades the saving for duplicate classification, which is the same spend it was trying to avoid. Paying Gemini once for that legacy backlog is the cheapest of the three, and it is the only option where correctness needs no argument.

  • (a) Both layers, in this change. Layer 1 (config): add -H 127.0.0.1 to package.json's start and retire the mc.local prod vhost from ~/.config/caddy/Caddyfile, so no LAN client can reach the origin at all; repoint launch-mc.sh's APP_URL. Layer 2 (code): new lib/access-jwt.ts verifies Cf-Access-Jwt-Assertion against the team JWKS with a per-app AUD and an email-claim cross-check, fail-closed. Pros: defence in depth across two independent failure modes — Layer 1 removes the attack surface, Layer 2 makes forgery fail cryptographically if Layer 1 ever regresses (a start-script tweak, a restored Caddyfile, a new proxy); both land before crew exist, so there is no window. Cons: the largest scope in the change; new env (team domain + per-app AUD); a hard manual prerequisite (the tunnel's origin URL) before the bind can flip; and it takes mc.local away from the owner.
  • (b) Layer 1 only — bind + retire the vhost, no JWT verification. Pros: zero code, immediate, and it genuinely closes today's forgery path since there is no route to the origin to forge over. Cons: the whole guarantee rests on a configuration property that regresses silently and invisibly — nothing in the test suite can assert "prod is not listening on the LAN," so a future -H removal or a re-added vhost reopens full impersonation with no signal.
  • (c) Layer 2 only — verify the JWT, leave the network as it is. Pros: the guarantee is cryptographic and testable, and it survives any network change. Cons: leaves the origin directly reachable from the LAN, so every unguarded or future surface (and the whole /api/gmail/webhook Bypass path) stays exposed to LAN traffic; and it makes the JWKS a hard availability dependency for all access with no network fallback in front of it.
  • (d) Neither — status quo. Pros: no work. Cons: role gating becomes decorative: any device on the home WiFi types one header and becomes the owner or any crew member. Given that the whole premise of this change is friends on that network, this is not a viable position.

✓ Decided: (a) — both layers, in the same wave, not deferred as hardening. (b) and (c) each close the hole through exactly one mechanism, and the two mechanisms fail in unrelated ways: configuration drifts silently, and a code-only check leaves the LAN pointed at the origin. Shipping both means a single regression is never sufficient to reopen impersonation. Three verified facts shape the tasks: loopback binding alone is not enough — Caddy proxies mc.local:443 → 127.0.0.1:3101, so retiring the vhost is load-bearing; there is only one Caddyfile — /opt/homebrew/etc/Caddyfile is a symlink to ~/.config/caddy/Caddyfile, so there is no stale duplicate to chase; and cloudflared runs token-based with no local config, so the tunnel's ingress URL is only visible in the dashboard — making a manual check (Zero Trust → Networks → Tunnels → Public Hostnames) a blocking prerequisite (P0.2 gates P4.1), because if a hostname targets a non-loopback address the bind takes prod offline.

OQ14 — How do the 10 integration suites authenticate once there is no network-trust path?

Added during the decision pass. A direct consequence of OQ2a: all 10 files under scripts/tests/integration/ call http://localhost:4101 with no identity header (verified — 10 suites, all 10 reference 4101), and test-integration.sh aborts unless mission-control-dev is online. Removing the header-less fallback 401s every one of them.

  • (a) A dev-only env break-glass. An env var — off by default — makes a loopback request on the dev tier resolve to the owner, hard-gated three ways (the var, a loopback remote-address check, and NODE_ENV !== 'production' in code), emitting one console.warn per process so an enabled escape is visible in the in-app log viewer. Pros: zero suite edits; the escape is explicit, discoverable in logs, and scoped to the tier that is owner-only anyway (OQ12a), so it grants nothing beyond the only identity on that tier; it also doubles as the on-box recovery pattern for prod (separate var). Cons: a bypass exists in the codebase, so it must be reviewed as security-relevant and can never be allowed to reach prod; and it needs an explicit carve-out from OQ13's JWT verification, since a loopback request carries no JWT.
  • (b) Add a forged identity header to all 10 suites. Pros: no production code path exists for tests to walk through. Cons: only works if the origin accepts forged headers — i.e. it requires abandoning OQ13's Layer 2 entirely, which is a far larger concession than a gated dev escape; and it would need re-adding to every future suite.
  • (c) Mint a service token for the suites, reusing the requireServiceToken pattern. Pros: uses an existing, constant-time-compared mechanism with no new trust concept. Cons: that pattern is per-service (tokenEnv + userIdEnv + a matching ?onBehalfOf=) and is wired into exactly one route today, so every suite's every request would need the Bearer header and the query param — a bigger, more invasive edit than (b) across all 10 files, plus a long-lived token in the dev env.
  • (d) Drop the integration suites. Pros: no auth question. Cons: loses the only tests that exercise real routes end-to-end against a live server; they are already outside the pre-push gate, so they cost nothing to keep and are the only safety net for exactly the kind of wiring this change touches.

✓ Decided: (a) — a dev-only, off-by-default, loudly-logged loopback break-glass; the suites need no edits. (b) would require giving up JWT verification, (c) is a larger edit than (b) for a token that then lives in the dev env indefinitely, and (d) discards the only end-to-end coverage of the surfaces being changed. Two constraints the implementation must honour: the production guard is a code condition (NODE_ENV), not a convention or a config comment; and OQ13 Layer 2's JWT verification must be skipped on this path — branch order is break-glass first, else strict — because there is no JWT on a loopback request. Getting that order backwards makes the escape dead code and the suites fail with a misleading JWT error.

  • Round 3: P1.4 ∥ P2.4 ∥ P3.1 — P2.4 is the long pole here (68 call sites); the other two are small.
  • Round 4 (widest fan-out — five agents): P2.1 ∥ P2.3 ∥ P2.5 ∥ P2.6 ∥ P3.2-P3.6. Every file conflict was resolved in Round 3.
