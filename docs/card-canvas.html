mission-control

CardCanvas

Replace CardGrid's fixed-breakpoint stretch-to-row-height grid with a container-driven, content-packed card engine — reclaiming the vertical dead space every short card currently pays for, and making column count respond to available width instead of viewport width.

Context & problem

Problem

Every dash renders its cards through components/grids/CardGrid.tsx (76 lines), used by all 8 views plus Section.tsx:48. Four distinct defects in that file produce the wasted space:

#DefectSiteCost
1 Row-height stretch. Items default to h-full; CSS Grid sizes a row to its tallest card, so every shorter sibling is stretched with its content pinned to the top and dead space below. CardGrid.tsx:61 The dominant waste. hFit is the opt-out but appears at only 14 sites against 47 span-prop usages — waste is the default.
2 Viewport breakpoints, not container-aware. Hard ladder grid-cols-1 md:grid-cols-2 lg:grid-cols-3, capped at 3 columns off viewport width. CardGrid.tsx:42–46 On a wide display, 3 over-wide columns instead of 4–5 sensible ones. Ignores the shell's own chrome, so the breakpoint fires at the wrong moment on mobile.
3 Masonry mode silently drops spans. Emits the class column-span-all, which is not a Tailwind utility and is defined nowhere in the repo — the string appears at exactly one place, its own emission site. CardGrid.tsx:60 colSpan is a no-op in masonry. Combined with multi-column's column-wise flow (DOM order ≠ visual order), masonry can't be used anywhere ordering matters.
4 Chrome cost is scattered literals. gap-4 + p-4 + Card's header mb-4, hardcoded. CardGrid.tsx:42,68, Card.tsx:46 No single density knob; tuning breathing room means editing three files.

The two card families

The constraint that shapes the whole design: the cards have already split into two families, and hFit is the existing marker. This is why "just make everything content-height" is wrong.

  • Family A — content-sized (the 14 hFit: true sites; all of ProfileView). These bound their own internal scroll regions with explicit caps — max-h-[16rem] in GeneratedResumesCard.tsx:149, max-h-[20rem] in CanonsCard.tsx:527, max-h-[24rem] in GenerateResumeCard.tsx:355. Content-height is free for these; they are already correct.
  • Family B — fill-height (8 files: KanbanWidget, CalendarWidget, MarketTop100Card, ResearchPaperCard, LLMLeaderboardCard, FetcherHealthCard, GoalCard, SnapshotsCard). These use flex-1 overflow-y-auto against a bounded parent — the pattern CLAUDE.md names as canonical. Content-sizing breaks them: KanbanWidget.tsx:121,129 is h-full throughout and collapses outright; the rest expand to full list height instead of scrolling.
Correction (2026-08-01) — there are three bounding patterns, not two. Implementation turned up a third way a scrolling card can already be bounded, which changed how many height tokens the migration actually needed. In preference order: (i) the card self-bounds in its own markup — FetcherHealthCard and CrewCard both open with h-[280px], InternalView's log and cache cards carry h-[400px] / max-h-[480px] md:h-[280px]; (ii) the call site caps the frame via the CardItem's className — PlanningView's max-h-[35vh]/max-h-[65vh] and ApplicationsView's two vh caps, which work because flex-1 min-h-0 resolves against a max-height; (iii) a height token, needed only where neither of the first two applies. Net effect: only 8 cards took a token, not the ~10 estimated, and InternalView — projected as a heavy migration — needed none at all. One real trap did surface: a percentage height (h-full) does not resolve against an auto-height parent, so cards that size through an h-full chain need a definite height rather than a max-height — see P2.4.
Family B is why this isn't a one-line fix. A masonry engine has no rows for a card to fill, so "stretch to fill" has no meaning in it. Every card must arrive at a resolved height — measured for Family A, declared for Family B. Resolving how Family B declares that height is OQ1.

Goals & non-goals

  • Goal: eliminate the stretch dead space — a card's height is its content's height (Family A) or an explicit declared height (Family B), never "whatever the tallest neighbour happened to be".
  • Goal: column count derives from container width, with no md:/lg: ladder, scaling past 3 columns on wide displays.
  • Goal: colSpan keeps working under packed layout (it does not today — defect 3).
  • Goal: one density knob via CSS custom properties, following the --section-gutter pattern already established at MobileShell.tsx:202.
  • Goal: layout must degrade correctly with JS disabled or pre-hydration — JS refines, it is never load-bearing.
  • Non-goal: drag-to-reorder / user-persisted card ordering. Ordering here means layout order (DOM order preserved under packing). Persisted per-user arrangement is a separate feature on the Zustand store — deferred.
  • Non-goal: redesigning card contents. This changes the container and its ordering, not what any card renders.
  • Non-goal: touching lib/cache.ts, any API route, or any data path. Pure presentation.

Design

Approach

A new engine, components/grids/CardCanvas.tsx, built as three independent layers. Each layer is useful alone and degrades to the one below it, which is what keeps JS off the critical path.

Layer 1 — fluid tracks, capped, with zero breakpoints

The md:/lg: ladder is deleted outright and replaced with one declaration:

grid-template-columns: repeat(
  auto-fill,
  minmax(
    max(var(--cc-card-min), (100% - (var(--cc-max-cols) - 1) * var(--cc-gap)) / var(--cc-max-cols)),
    1fr
  )
);

The inner max() is the load-bearing trick. A plain minmax(20rem, 1fr) grows columns without limit on a wide display; taking the max against one --cc-max-cols-th of the container means a track can never be narrower than that share, so the track count can never exceed --cc-max-cols. Below that width it falls back to --cc-card-min and reflows fluidly. This caps the column count in pure CSS, with no measurement and no breakpoints — and because it is expressed in 100% of the grid element, it responds to container width, which is what makes it correct inside DesktopShell, MobileShell, and any future split pane alike.

Span mapping is likewise static — resolvable at render from the declared props, no JS:

  • colSpan === columns (i.e. the caller meant "full width") → grid-column: 1 / -1. This covers the majority case: 6 of 9 InternalView cards, all 4 PhysicsView cards, both PlanningView cards.
  • otherwise → grid-column: span N, which CSS Grid already clamps to the available track count.
Why colSpan must be read relative to columns. Today colSpan is a raw track count against a fixed 3- or 2-column grid, so colSpan: 2 means two-thirds width in AIView but full width in ApplicationsView (columns={2}, see ApplicationsView.tsx:244's own comment saying exactly this). Interpreting it as the fraction colSpan / columns preserves both intents under a variable track count.

Layer 2 — packing

True masonry via the row-span technique: the canvas sets a fine grid-auto-rows: var(--cc-row) with row-gap: 0, and each card is given grid-row-end: span ceil((h + gap) / row) where h is its measured content height. The visual row gap is baked into the span rather than applied by the grid.

Chosen over CSS multi-column (today's layout="masonry") because it is the only packing approach that keeps all three properties at once:

PropertyMulti-column (today)Row-span trickNative grid-lanes
Packs out vertical gapsyesyesyes
Preserves left-to-right DOM orderno — flows down column 1 firstyesyes
colSpan honouredno — dead class, defect 3yesyes
Browser supportuniversaluniversalSafari 26 only

A ResizeObserver per card feeds the measurement; a single observer instance on the canvas watches all children, so cost is one observer per section, not per card. Measurement targets the inner content element — not the motion.div frame, whose overflow-hidden (CardGrid.tsx:54) would otherwise clip the value it is meant to report.

JS is a refinement, never a dependency. With no JS — pre-hydration, or if the observer never fires — Layer 1 alone still yields a fluid, container-driven grid with align-items: start, i.e. content-height cards with row gaps left in. That is already strictly better than today's stretch. Layer 2 only closes the remaining gaps. This is deliberate: a layout that blanks or collapses when JS is late is not acceptable for the app shell.

Layer 3 — density tokens

--cc-gap, --cc-pad, --cc-card-min, --cc-row, --cc-max-cols, declared in app/globals.css and overridable per shell exactly as --section-gutter already is at MobileShell.tsx:202. The hardcoded gap-4 / p-4 / mb-4 literals become var() reads, so density is one knob rather than a three-file edit. Values are OQ5.

Alternatives considered

  • Pure-CSS only (no measurement). Layer 1 + align-items: start, stop there. Kills the interior stretch and the breakpoint ladder for ~10 lines and no JS at all. Rejected as the endpoint because it leaves the between-row gaps — the second half of the reclaimed space — but it is retained as the degradation target, which is what makes Layer 2 safe to add.
  • Native display: grid-lanes as the primary mechanism. Shipped in Safari 26; Chrome and Firefox still behind flags as of early 2026, and the property was renamed from the earlier grid-template-rows: masonry spelling. Rejected as primary — it would leave two of three engines unpacked — but adopted as a progressive-enhancement layer behind @supports, where it costs one CSS block and lets the JS bail out entirely.
  • A JS masonry library (Masonry, Muuri, react-masonry-css). Rejected: a new runtime dependency for ~40 lines of arithmetic, most of them absolutely-positioning items — which would break the existing framer-motion frames, the hover:z-10 lift at CardGrid.tsx:54, and the portalled popovers that CanonsCard.tsx:430 and GenerateResumeCard.tsx:606 already work around overflow-hidden for.
  • Container queries (@container) for the column count. Tailwind v4 supports these natively with no plugin, and they were the obvious candidate for "make it reactive". Rejected in favour of auto-fill + max(): container queries would reintroduce a breakpoint ladder, merely one keyed to the container instead of the viewport, whereas the max() formula is continuous and needs no thresholds at all. Container queries stay available for intra-card layout later — a genuinely different problem.

Rollback

Cheap by construction, and the mechanism depends on OQ3. If CardGrid keeps its public CardItem API (options a/b), reverting is a one-file revert of the shim — no view touched, no data touched. This change writes no schema, no migration, and no route, so there is nothing to un-migrate and no DB tier to bring current; the entire blast radius is presentation.

Full back-out: git revert the merge, npm run build, pm2 restart mission-control. The worktree (worktree-card-canvas) keeps main clean until the change is proven on the dev tier, so the pre-merge state is always one branch switch away.

Open Questions

Unresolved decisions

Five genuine forks. OQ1 was the blocking one — it decided whether 8 card files need edits, which in turn sized the whole task list.

All five resolved 2026-08-01. OQ1 → (b), OQ2 → (a), OQ3 → (b), OQ4 → (a), OQ5 → (a). The Tasks section below is authored against these decisions. Options are kept under each question as the record of what was weighed.
OQ1 — How does a Family B (fill-height) card declare its height once there are no grid rows to fill?
  • (a) Reinterpret rowSpan as a height multiplier. Keep the existing prop; rowSpan: 2 stops meaning "span 2 grid rows" and starts meaning "2 × a base height unit" (e.g. 2 × 14rem = 28rem). Only FinanceView.tsx:92,113 uses it today, so no call site changes. Pros: zero view edits; the two existing users keep working. Cons: the prop name becomes a lie — rowSpan that doesn't span rows is exactly the kind of drift that makes a component hard to reason about later, and it silently gives every Family B card the same height whether or not that suits it.
  • (b) New explicit height prop with named tokens. Add height?: "auto" | "sm" | "md" | "lg" | "xl" to CardItem, defaulting to "auto" (content-measured). The 8 Family B cards get an explicit token at their call sites; rowSpan is deleted. Pros: says what it means; each card gets the height that actually suits it; the token set keeps heights consistent instead of 8 arbitrary pixel values; auto-by-default means Family A needs no annotation at all. Cons: touches the ~10 call sites that render Family B cards, and someone adding a new scrolling card must remember to set it — mitigated by the non-zero-height smoke.
  • (c) Auto-detect at runtime. Measure whether a card's subtree contains a flex-1/overflow-y-auto descendant and switch that card to fill mode automatically. Pros: no API change and no call-site edits at all. Cons: magic — layout silently depends on a CSS class deep in a child's markup, so an unrelated refactor inside a card changes its outer height with no visible cause; and it can't decide how tall, only that it's bounded, so it still needs a default. Fragile in exactly the way the two-families problem is already subtle.

✓ Decided: (b) — add height?: "auto" | "sm" | "md" | "lg" | "xl" to CardItem (default "auto") and delete rowSpan. The two families are a real distinction the code currently expresses only accidentally via hFit, and (b) is the only option that makes it explicit and per-card; (a) preserved call sites at the cost of a prop whose name no longer describes what it does, and (c) bought zero edits by making a card's outer height depend on invisible descendant markup. The auto default means Family A needs no annotation at all, so the edit cost falls only on the ~10 Family B call sites.

OQ2 — Does the columns prop become a maximum, or stay an exact column count?
  • (a) columns becomes a cap. It feeds --cc-max-cols; the grid uses as many tracks as fit up to that number and fewer when narrow. ApplicationsView's columns={2} stays at most 2 wide; the default-3 views stay at most 3. Pros: preserves every view's designed information hierarchy (a kanban board spread to 5 tracks would be wrong) while still reflowing down fluidly; one-line migration. Cons: ultrawide displays still stop at 3 columns for most views, so part of the horizontal-space win needs a per-view opt-in to a higher cap.
  • (b) Drop columns; derive purely from --cc-card-min. Column count is whatever fits at the minimum card width, uncapped. Pros: maximum space reclamation on wide displays; genuinely one continuous rule with no per-view knob. Cons: destroys deliberate 2-column compositions — ApplicationsView's calendar/kanban pairing and ProfileView's columns={2} sections become 4- or 5-up on a wide screen, which is a layout regression, not a win.
  • (c) Cap by default, with an explicit maxColumns override. As (a), plus views that genuinely benefit from more tracks (the news grids in SpaceView and AIView, which are uniform small cards) pass a higher number. Pros: safe default plus the ultrawide win exactly where it helps. Cons: two props that mean nearly the same thing, which invites confusion about which one to reach for.

✓ Decided: (a) — columns feeds --cc-max-cols and acts as a cap. It is a strictly-safe reinterpretation of every existing call site, and the news-grid case that motivated (c) is served later by simply passing a larger columns value rather than adding a second prop that would need explaining. (Taken as the stated default when the other four were resolved; ship-first, revisit if ultrawide still feels sparse.)

OQ3 — How does the new engine reach the 8 views?
  • (a) Reimplement CardGrid in place. Keep the filename, the export, and the CardItem API; swap the internals. No view imports change. Pros: smallest diff; every view gets the improvement at once; rollback is a one-file revert. Cons: no side-by-side comparison — the change lands everywhere simultaneously, so a regression in one view can't be isolated by toggling that view alone.
  • (b) New CardCanvas; CardGrid becomes a thin shim over it. Both names work; views migrate to CardCanvas one at a time to opt into new props like height. Pros: gradual, per-view migration; the shim keeps un-migrated views on today's exact behaviour; a bad view reverts independently. Cons: two components coexist during migration, and a half-migrated repo is a state someone has to hold in their head.
  • (c) New CardCanvas, migrate all 8 views at once, delete CardGrid. Pros: ends clean with one component and no shim debt. Cons: largest single diff, touching all 8 views plus ~47 span-prop call sites in one change — the hardest version to review and the hardest to bisect if something looks wrong.

✓ Decided: (b) — build CardCanvas and make CardGrid a shim over it. It is the only option that lets the engine be proven on one view against the running dev tier before the other seven move, which matters because the failure mode here is visual and per-view rather than something tsc or a smoke will catch. The shim is deleted in the final task (P3.3), so (b) converges on (c)'s clean end state without (c)'s reviewability cost.

OQ4 — Is content-packing the default for every section, or opt-in per canvas?
  • (a) Packed by default. Every canvas packs; a section opts out with layout="rows" to get today's aligned-row behaviour. Pros: the space win applies everywhere without per-view work, which is the stated goal; the existing layout="masonry" call site in SpaceView.tsx:387 just becomes the default and its broken colSpan handling is fixed for free. Cons: sections whose cards are deliberately equal-height lose their tidy alignment, and staggered card bottoms can read as visually noisier on dense dashes like InternalView.
  • (b) Opt-in per canvas. Default stays aligned rows; sections pass layout="packed". Pros: nothing changes visually until each section is deliberately opted in, so the rollout is incremental and every change is intentional. Cons: the wasted space this doc exists to reclaim persists everywhere until someone goes view by view — the default stays the bad one, which is how the current hFit situation arose in the first place (14 opt-ins against 47 sites).

✓ Decided: (a) — pack by default, with an explicit layout="rows" escape hatch. The hFit precedent is the direct evidence: an opt-in space-saving flag reached only 14 of 47 eligible sites, so leaving the wasteful behaviour as the default predictably means it stays. Making the good behaviour the default and the exception explicit inverts that, and it fixes SpaceView's silently-broken layout="masonry" (defect 3) as a side effect.

OQ5 — What are the density token values, and is density user-facing?
  • (a) Tokenise at today's values; change nothing visually. --cc-gap: 1rem, --cc-pad: 1rem — exactly the current gap-4/p-4. All space reclaimed comes from packing alone. Pros: isolates the change; any visual difference is provably from the layout engine, not from restyling, which makes the diff far easier to judge. Cons: leaves the per-card chrome savings on the table in this pass.
  • (b) Tokenise and tighten now. Ship at --cc-gap: 0.75rem, --cc-pad: 0.75rem. Pros: visibly denser immediately, compounding with the packing win. Cons: conflates two changes in one diff — if the result feels wrong it's ambiguous whether the packing or the tightening caused it; and 0.75rem is off the power-of-2 spacing steps this project prefers.
  • (c) Tokenise and expose a comfortable/compact toggle persisted in the Zustand store alongside isDarkMode and viewHues. Pros: makes density a user choice rather than a guess. Cons: a settings surface, a store field, and a sync path for what is currently a two-value CSS variable — clearly a v2 given the preference for a minimal first cut.

✓ Decided: (a) — tokenise at today's values (--cc-gap: 1rem, --cc-pad: 1rem) and tune separately once the packing is visible. Keeping the engine change and the density change in separate diffs is what makes the result attributable to one of them; the tokens are the enabling work either way, so (b) stays a one-line follow-up and (c) a later feature on top of the same variables.

Rounds & critical path. Round 1: P0.1 alone (blocks everything). Round 2: P0.2 ∥ P0.4. Round 3: P0.3 ∥ P0.5 ∥ P3.1 — the smoke starts here and runs concurrently with everything downstream. Critical path: P0.1 → P0.2 → P0.3 → P1.1 → P1.2 → P2.x → P3.2 → P3.3. P0.2 is the most-constrained node — it is the only task with real algorithmic content (the measurement hook and the track formula), everything downstream waits on it, and it cannot be split without two agents editing one file. Schedule it first and give it the most care; the seven-way fan-out in Round 5 is wide but mechanical, and is not where the risk lives.
