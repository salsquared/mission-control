Cloudflare Access auth at the edge

Context & problem

Problem

Mission-control is a single-user personal app reachable two ways: directly on the LAN (localhost, 127.*, 0.0.0.0, mc.local, phone-on-WiFi), and over the public internet through a Cloudflare tunnel (cloudflared, system-level via Homebrew). Two tiers sit behind the tunnel: prod (PM2 mission-control, :3101, prisma/prod.db) and dev (PM2 mission-control-dev, :4101, prisma/dev.db).

Today the only thing between the open internet and the UI is the Google OAuth sign-in screen, enforced by three guards in lib/auth-guards.ts:

  • requireSession() (lib/auth-guards.ts:6) — used by 43 route files; returns { session }, and handlers read session.user.email and session.user.id (51 session.user reads across the API surface).
  • requireLocalOrSession(req) (lib/auth-guards.ts:128) — used by 20 route files; LAN hosts in LOCAL_HOSTS (lib/auth-guards.ts:77) with an all-private X-Forwarded-For chain skip auth, anything else needs a session or gets 401.
  • requireSessionOrService(req, config) (lib/auth-guards.ts:60) — used by 1 file (app/api/calendar/event/route.ts, all three methods); accepts a Bearer service token (Pulsar) or a session, returns { userId }.
  • requireServiceToken(req, config) (lib/auth-guards.ts:26) — strict service-token check; not changed by this work (0 direct route callers today; reached only via requireSessionOrService).

This design has two concrete failures:

  1. The page shell loads for anyone. app/page.tsx mounts Dashboard client-side (ssr: false), so the React shell + dash carousel + Launchpad render for any visitor who reaches the hostname. Only data routes 401 — the empty card frames are already on screen. For a single-user app, nobody else should reach it at all.
  2. Logged-out-of-Google means "not loading." When the owner's NextAuth session lapses, requireSession 401s every data route and the UI 401-cascades into a sea of empty frames and "Sign in" walls — even though the owner is the only person who will ever use the app. Four components gate directly on useSession: components/views/ProfileView.tsx:31,234 (renders a "Sign in" wall, query enabled: Boolean(session) at :37), components/views/ApplicationsView.tsx:61,323 ("Connect Workspace" wall; both list queries gated at :91/:96), components/widgets/CalendarWidget.tsx:48-49,55 (userId from session, query gated on it), and components/views/InternalView.tsx:48,520,509 (manual signIn('google') / signOut() controls).

The sibling project wc26stats already fronts itself with Cloudflare Access, configured purely at the Cloudflare edge / Zero Trust dashboard — there is no app code for it; the origin simply trusts the edge. We adopt the same pattern here. Google OAuth then goes back to its real job: holding the long-lived Gmail + Calendar refresh token on the Account row (lib/auth.ts:69-84), consumed by lib/googleapis.ts:getGoogleAuthClient.

Ground truth confirmed. Both prisma/dev.db and prisma/prod.db currently hold exactly one User row — salsalcedo4321@gmail.com — each with a Google Account that has a non-null refresh_token (verified 2026-06-24). The "single owner" assumption the whole design rests on is real today.

Goals & non-goals

  • Goal: Nobody but the owner can reach any surface (shell or data) over the public tunnel — enforced at the Cloudflare edge before the request ever reaches the origin.
  • Goal: The owner, once past Access, is treated as always authenticated — no in-app "Sign in" wall, no 401-cascade when Google logout lapses. The app is usable purely on the strength of having passed Access.
  • Goal: Google OAuth is retained but reframed — it exists only to obtain / refresh the Gmail + Calendar token, surfaced as a non-blocking "Connect / reconnect" affordance, never as the access gate.
  • Goal: Centralize the change. Rewrite the 3 guards (+ one owner-resolution helper) so ~60 route files and their session.user.* reads keep working untouched.
  • Goal: Pub/Sub webhook (/api/gmail/webhook) and local service callers (Pulsar) keep working — Access must not block machine traffic that can't do an interactive login.
  • Non-goal (v1): Origin-side verification of the Cf-Access-Jwt-Assertion JWT (team domain + per-app AUD). Deferred — see OQ3; noted as future hardening in Risks.
  • Non-goal: The earlier "in-app passcode gate" approach sketched in docs/user-stories.md (S15.x). This design supersedes it: the gate moves to the edge instead of being a new application-level passcode. Update user-stories.md framing as part of the docs phase.
  • Non-goal: Multi-user / team support. The design is deliberately single-owner; revisit only if a second user is ever added.

Design

Approach

The change splits cleanly into edge config (no code — done in the Cloudflare Zero Trust dashboard) and a small, central code change at the origin. The key insight that keeps the diff tiny: rewrite the three guards plus one new owner-resolution helper, and the ~60 route files that call them — along with all 51 session.user.* reads — keep working with no per-file edit.

Trust model — trust the edge

The origin does not verify the Access JWT (OQ3). The reasoning is a closed-world argument about inbound paths: the only ways a request reaches the origin are (a) the LAN — already trusted today via the requireLocalOrSession bypass — and (b) the Cloudflare tunnel, which only forwards a request after Access has authenticated it at the edge. There is no third path. So any request that arrives is, by construction, either LAN-local or Access-passed — both legitimately the owner. The origin treats every arriving request as the owner. This keeps the code minimal and needs no team-domain / AUD configuration in the app.

One narrow exception: /api/gmail/webhook is reached by Google's Pub/Sub servers, which cannot do an email-OTP login — so Access must bypass that path at the edge (OQ4). It stays authenticated by its own Google-signed OIDC check (verifyPubSubOIDC, app/api/gmail/webhook/route.ts:33 + the signer-email assertion at :34-41). Only Google can call it. This bypass is the one place where "trust the edge" doesn't apply, and it's safe precisely because that route carries its own independent auth.

Server — owner resolution + three guard rewrites

Add a single owner-resolution helper — resolveOwner() — returning { id, email } for the single owner User. Resolution order, deterministic and minimal:

  1. If OWNER_EMAIL env is set → prisma.user.findUnique({ where: { email } }).
  2. Else → the single User row (findFirst, stable order by createdAt for determinism if a stray second row ever appears).
  3. Zero users (fresh machine, no Google connected yet) → return null; callers degrade gracefully (the synthesized session is absent, the connect affordance shows). This is the only "0 users" branch and it must not throw.

Because it's called per-request across ~60 routes, memoize the resolved owner id + email in a module-level variable (single-user ⇒ effectively immutable for the process lifetime). Invalidation is rarely needed; a small TTL (e.g. 60s) or a "re-resolve on null" rule covers the fresh-connect case where the first User row appears after boot. Flag this as the one perf-sensitive spot (OQ-free; the memo is the obvious minimal choice).

The three guards (all in lib/auth-guards.ts) are rewritten to stop calling getServerSession and instead resolve the owner — preserving their exact return shapes so callers don't change:

The synthesized session must populate both user.id and user.email — handlers read both (e.g. app/api/applications/backfill/route.ts:37 reads session.user.email; calendar/profile/resume routes read session.user.id). It need not populate user.name / user.image — those are only used cosmetically in the client (avatar / name in Account Status cards), which now come from the account endpoint instead.

Frontend — owner is always authenticated

Four components gate on NextAuth's useSession; a fresh device that passed Access would otherwise hit a dead "Sign in with Google" wall. Introduce a tiny client seam (OQ-free implementation detail, decided below):

  • New route GET /api/account returning { user: { id, email }, googleConnected: boolean }, where googleConnected reflects whether the owner's Account row has a usable refresh_token + the required scopes. Guard it with the rewritten requireSession() (so it returns the owner; 401 only on the 0-users fresh-machine state). Add its sibling app/api/account/meta.ts per the generated-API-docs convention and regenerate apis.html.
  • New hook useAccount() (e.g. hooks/useAccount.ts) wrapping a react-query fetch of /api/account. The four components consume it instead of useSession.

Behavior after the swap:

  • ProfileView / ApplicationsView — never show the access wall (owner is always present once past Access). The profile / applications queries become enabled on owner presence. They surface a non-blocking "Connect Gmail / Calendar" affordance only when googleConnected === false (the token is missing or scopes are stale) — not as a gate, as a banner/button inside the otherwise-functional view.
  • CalendarWidget — takes userId from the owner (useAccount().user.id) instead of session?.user?.id.
  • InternalView — keeps signIn('google') + signOut() as manual token management, reframed as "Connect / Reconnect Google" and "Disconnect". The avatar/name block reads from useAccount() (and may simply show the owner email + connected/disconnected state).

Keep NextAuth's SessionProvider mounted in app/layout.tsx:58 (via components/providers/SessionProvider.tsx) — it's still needed for the connect/reconnect flow that signIn('google') drives. We do not drop the provider (see Alternatives).

Google OAuth / NextAuth — kept, reframed

lib/auth.ts stays as-is in structure: the Google provider with offline access + the Gmail/Calendar scopes (lib/auth.ts:24-41), the signIn callback that persists the refresh token and arms the Gmail watch (lib/auth.ts:46-101), and allowDangerousEmailAccountLinking (lib/auth.ts:23). It now exists only to obtain / refresh the token — not to gate access. Keep the ALLOWED_SIGNIN_EMAILS allowlist in the signIn callback (lib/auth.ts:51-63, helpers in lib/auth-allowlist.ts) as defense-in-depth on the connect flow: even though Access already gates who reaches the connect button, the allowlist ensures a stray OAuth completion can't link a non-owner account. NEXTAUTH_URL is already per-tier correct in the env examples.

  • Test: hermetic smoke for resolveOwner() + the synthesized-session guard returns.

Alternatives considered

  • Verify the Access JWT at the origin (defense-in-depth). Read Cf-Access-Jwt-Assertion, validate signature against the team's public keys, check the per-app AUD. Rejected for v1 (OQ3): the closed-world inbound argument already guarantees authenticity, and verification adds origin code + team-domain/AUD config for no marginal protection in a single-owner topology. Kept as a future-hardening note in Risks.
  • A separate non-Access webhook hostname for Pub/Sub. Rejected (OQ4): adds a tunnel hostname + Pub/Sub subscription reconfig (the audience must match the endpoint URL) for no benefit over a path-scoped Bypass app, which Cloudflare evaluates at higher precedence than the hostname app.
  • In-app passcode gate (the prior user-stories.md S15 sketch). Rejected: it's new application code to maintain, still ships the shell to anyone before the passcode prompt unless every route + the shell are gated, and duplicates exactly what the edge already does for free in wc26stats. Edge-gating is strictly less code and gates the shell too.
  • Drop SessionProvider entirely. Rejected: the connect/reconnect flow (signIn('google')) still needs NextAuth client context. Keeping the provider mounted is cheap and avoids reworking the connect path.
  • Edit each of the ~60 route files to read the owner directly. Rejected: enormous diff, high regression surface, and pointless — the guards are already the single choke point. Centralizing in the 3 guards + 1 helper is the whole reason the change is small.

Rollback

Two independent levers, either direction:

  • Edge: remove (or disable) the four Access apps in the Zero Trust dashboard — the hostnames revert to whatever the origin enforces.
  • Origin: git revert the guard rewrite + frontend swap, rebuild, pm2 restart mission-control mission-control-dev. This restores the old requireSession / requireLocalOrSession behavior exactly (the change is code-only — no schema migration, no data change, so revert is clean).

Because the rollout order is "edge first, then code," the safe rollback is the reverse: revert the code first (the in-app gate returns), then optionally remove the edge apps. There is never a window where both gates are absent if the order is respected.

Open Questions

Resolved decisions

OQ1–OQ4 were settled with the owner before this doc was written; they are recorded here as the decision record (options kept, pick appended). One genuinely-new fork surfaced during file review — the exact prod hostname — flagged OPEN-A; it is now resolved → (a) from the live .env.production (prod = ms-prod.salsquared.xyz). No open questions remain. ⚠ OPEN-A was later superseded (2026-07-27) — the hostnames are now mc.salsquared.xyz / mc-dev.salsquared.xyz; see the superseding note at the end of this section.

OQ1 — What Access session lifetime should the prod hostname use?
  • (a) 24 hours. Set the prod Access app's session duration to 24h, so a passed login is re-prompted once per day. Pros: a session leaked from an untrusted/random computer expires within a day; bounds blast radius tightly. Cons: the owner re-authenticates daily even on their own devices (one click each time).
  • (b) 1 week. Set prod to a 7-day session. Pros: fewer re-auth prompts. Cons: a session captured on an untrusted machine stays valid for up to a week — too long for a host the owner may sign in from on a random computer.

✓ Decided: (a) — prod (mc.salsquared.xyz, ms-prod.salsquared.xyz when decided) session lifetime = 24 hours, because the owner may sign in from an untrusted/random computer and a leaked session should expire within a day; the daily re-auth cost is one click.

OQ2 — What Access session lifetime should the dev hostname use?
  • (a) 1 week. Set the dev Access app to a 7-day session. Pros: shorter exposure window than a month. Cons: unnecessarily frequent re-auth on the owner's own devices, which is the only place dev is ever opened.
  • (b) 1 month. Set dev to Cloudflare's longest preset for email-identity sessions (~1 month; there is no true "forever"). Pros: minimal re-auth friction on trusted own-devices; re-auth is one click when it does lapse. Cons: a leaked dev session lives up to a month — acceptable because dev is only accessed from the owner's own devices and exposes the same single mailbox.

✓ Decided: (b) — dev (mc-dev.salsquared.xyz, ms-dev.salsquared.xyz when decided) session lifetime = 1 month (the longest email-identity preset), because dev is only ever opened from the owner's own devices, so re-auth friction is the dominant cost and the longer window is safe.

OQ3 — Should the origin verify the Cloudflare Access JWT, or trust the edge?
  • (a) Trust the edge (no origin verification). The origin reads no Access header and verifies no JWT; it treats every arriving request as the owner, relying on the closed-world fact that the only inbound paths are LAN (already trusted) and the tunnel (only forwards Access-passed requests). Pros: minimal code; no team-domain / per-app AUD config in the app; nothing to keep in sync with the edge. Cons: if a future change ever exposed a non-tunnel, non-LAN inbound path, the assumption breaks (mitigated by it being documented + the future-hardening note).
  • (b) Also verify Cf-Access-Jwt-Assertion at the origin. Validate the JWT signature against the team's public keys and check the per-app AUD on every protected request, in addition to the edge gate. Pros: defense-in-depth; the origin is self-protecting even if the inbound topology changes. Cons: more origin code, plus team-domain + per-app AUD configuration to provision and maintain — redundant in the current single-owner topology.

✓ Decided: (a) — trust the edge for v1, because the only inbound paths are LAN (trusted) and the Access-gated tunnel, so any arriving request is already authenticated; (b) is retained as a future-hardening option in Risks should the inbound topology ever change.

OQ4 — How should the Gmail Pub/Sub webhook be exempted from Access?
  • (a) Path-scoped Access Bypass on /api/gmail/webhook. Create a path-scoped Access app for <HOST>/api/gmail/webhook on each hostname with a Bypass / Everyone policy, so Pub/Sub's OIDC-signed POST reaches the origin; the route keeps its existing verifyPubSubOIDC + signer-email assertion. Path-scoped apps take precedence over the hostname app. Pros: no new hostname, no Pub/Sub reconfig; the webhook keeps its independent Google-signed auth; smallest change. Cons: one extra Access app per tier to manage (4 apps total).
  • (b) A separate non-Access webhook hostname. Route Pub/Sub to a distinct hostname with no Access app in front. Pros: clean separation of machine vs human traffic. Cons: adds a tunnel hostname AND a Pub/Sub subscription reconfig (the OIDC audience must match the new endpoint URL exactly) for no benefit over a Bypass app.

✓ Decided: (a) — path-scoped Access Bypass on /api/gmail/webhook for both hostnames, keeping the route's existing Google-signed OIDC auth; Pub/Sub can't do interactive login so the path must bypass, and the route is already self-authenticated, so no new hostname or audience reconfig is warranted.
